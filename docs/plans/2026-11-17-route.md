# The cc-desk route

cc-desk ships in seven rounds. The first proves the seven untested behaviors the design rests on,
and every later round is designed only after that proof's findings are in, so the later rounds
carry outcomes and rough sizes here, not detail. Two changes from the starting cut: the session
round and the page round can run side by side, and the retire round now covers the whole old
system under Geoff's standing approval.

Design: [2026-11-17-cc-desk-design.md](../specs/2026-11-17-cc-desk-design.md). "Done item N"
below means item N of its "What done looks like" list.

### Why the cut changed

- **Sessions and Page run side by side.** Both rest only on the state files from State and rules,
  and their files don't overlap: the session code under the Go command, the page in a separate
  app folder. Each runs one pass at a time, which keeps the host at the two-building-pass limit.
  The design lets a plan record which rounds can run side by side ("What a round does at an
  unanswered question").
- **Done items 1 and 5 are split.** Both name the widget, which is part of the page. State and
  rules proves the figures and the "Ready now" verdict in the command's snapshot, and Page proves
  the widget shows them.
- **Done item 4 is split.** The rulings log, its guard, and both refusals live in the command, so
  they land in State and rules. Geoff typing a ruling at a desk session needs that session, so
  the item closes in Desk and skills.
- **Done item 6 is split.** It needs a conductor, which the skills in Desk and skills bring, and
  it says "the page shows". Sessions checks each recovery against the command's snapshot, with a
  stub conductor: a small script under the round's test folder that runs as a conductor would, so
  a killed conductor can be relaunched. Desk and skills checks the page half with the real
  conductor.
- **Retire is wider.** Geoff's ruling of 2026-11-17 adds the repos, records, and leftovers listed
  below.

### Two items from Geoff's rulings of 2026-11-17

**Sessions: a pass finishes with no permission prompt.** Geoff wrote:

The Sessions round carries this as a done item that can fail:

- A full pass launched by cc-desk finishes with no permission prompt.
- Every prompt that does occur is written to the state file with its cause.
- The round's report counts those prompts.
- Each one is filed as a defect against the launch settings, one follow-up file each.

Proof 4 sets the launch this item starts from.

**Page: the page opens the terminal desk.** Geoff wrote:

<!-- vale Vale.Spelling = NO -->
> it would be nice UI/UX if the web interace could pull up a terminal with cc-desk as it needed
> so I don't have to. But that's not critical.
<!-- vale Vale.Spelling = YES -->

This item is not critical, and the round can close without it.

- The page still writes nothing. It shows a link of the form `cc-desk://<project>/<round>`.
- A `.desktop` file registers a handler for that scheme with an `x-scheme-handler` MIME type.
  The handler runs `ptyxis -x "cc-desk <project> <round>"`.
- The round's plan probes Chromium's prompt for an outside protocol, and how to allow it once.
- Fallback: a button that copies the command.

### Which proofs bear on which round

Proofs 1, 2, 4, 5, and 6 shape the check and the launcher in Sessions. Proof 3 sets the launch
line's tool list there too. Proof 7 decides whether the usage stop in State and rules reads the
figure itself or takes it from conductors. A fallback that applies makes the round that rests on
it smaller or different, and that round's design says which.

## How each later round is cut

- Each pass is cut along file lines, and no pass edits a file every pass shares. Follow-up items
  are one file each under `docs/follow-ups/`, so no pass edits a common backlog.
- Within a round, the pass that rests on the least-proven assumption goes first. In Sessions that
  is the check, since it rests on proofs 1 and 2.
- A round is designed only after the one before it has its findings or its report, and designs
  stay at most two rounds ahead of the building.

## The retire round

Geoff ruled on 2026-11-17: "obviously the plan should include cleanup up all the old
infrastructure, removing repos, etc." Asked about the cleanup and teardown, he answered the same
day: "You have approval now." That answer is a standing approval. The round doesn't stop to ask
him before the teardown, and so it doesn't need Geoff.

The approval doesn't change the order of the work:

1. The round starts only after cc-desk passes done items 1 to 9. The old system runs until then.
2. It runs the `retire-project` skill in order: inventory, dry run, an encrypted archive of
   everything it deletes, the teardown, and the reference sweep. Nothing is deleted before
   its archive exists.
3. Its report lists everything it removed.

What it removes:

- The `approval-queue` repo, through `retire-project`.
- The queue's systemd service and the reminder hook in `settings.json`.
- The `desk` launcher, `round-watch`, and `claude-worktree-busy`.
- The `approval-packet` skill, and the desk and round references in `pass-core`.
- `~/.local/state/desk/`.
- Stale worktrees and `-wt` folders the old rounds left.
- The `glw907/cc-desk-scratch` repo the Prove round made for proof 4.
- Every prompt or doc that names a removed form, found by the search in `pass-core`
  `references/ready.md` "A retired form".

It closes the approval-queue and approval-packets initiative records and doesn't delete them.

Two places where the ruling departs from the design:

- The design keeps `~/.local/state/desk/` "as a record that nothing reads". The ruling removes
  it. The encrypted archive keeps the record.
- Done item 10 says the `approval-queue` repo "is archived". `retire-project` goes further and
  tears the repo down after its encrypted archive, which keeps the archived copy the item asks for.

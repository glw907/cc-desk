## Why this round

Geoff's rule for the desk round (2026-11-19): "That goal is to have the system we're building
evolve based on this mistakes." The desk round waited on him for about 30 hours across 25 stops.
Most of that time went to three causes. A rule stopped a pass whenever its plan came out larger
than the round's guess, which compared two forecasts. The landing test read a reviewer's word
where it should have read the findings. And a conductor that watched sessions in a loop missed
stopped ones, or blocked itself on a question.

cc-desk already answers some of this. A question is a record, the merge belongs to a timed check,
and a pass reports its review as data. The rest is still open: cc-desk has no budget, no place
for a standing answer, and no way to tell a stopped session from a working one. Cairn and
dubplate join cc-desk once 1.1 lands (Geoff, 2026-11-20), so 1.1 is the bar they join at.

Geoff set a second bar while this design was written (2026-11-20): "I do want to make sure that
cc-desk remains streamlined and easy to maintain as claude-code evolves", and "a lot of complex
Go code tied to an evolving process could be a risk." cc-desk is 11,654 lines of Go outside its
tests at `43c0669`. The section "What goes in Go" turns his words into a test that every change
in this design passed. Nine things the playback held were cut or moved by it.

## Goals

- Every row of the lessons file has an answer on the cc-desk side and on the `pass-core` side.
- A plan's size never stops a pass. A budget on the release bounds the round from measured
  minutes.
- The timed check does the routine watching. A session that stopped or finished early is seen
  within one check, with no conductor in a loop.
- A standing answer is a record that every launch prompt prints.
- cc-desk runs a round of its own repo with no conductor, and its report counts what it asked
  Geoff.
- A change to `pass-core`'s rules is an edit to text, and the Go stays as it is.

## What would make it a failure

- The second round asks Geoff a question he answers as recommended with no discussion. The
  report counts these, and each one is a missing standing answer.
- The page says "Needs you now" when nothing is his to decide, as it does today for the report's
  conductor.
- A pass waits on a figure, a branch, or a session that a check could have read.
- The budget stops a round that was working, or fails to stop one that ran away.
- The `pass-core` edits change a rule under the cairn or dubplate rounds while they run, and
  nobody tells their conductors.
- A pass writes one of `pass-core`'s rules into Go, so that the next change to the process needs
  a release of cc-desk.
- A pass adds a read of a file Claude Code keeps for itself.

## Approaches

Three ways to build this were on the table, and Geoff picked the third (2026-11-20).

1. One round under a conductor. Familiar, and it would prove nothing about cc-desk running a
   round. The first proof would be cairn's work.
2. cc-desk runs everything from the start. It would run its own repairs on the code that needs
   them: today's check can't launch its report's conductor and can't see a stopped session.
3. Two rounds. A conductor runs the first, which holds every change the check and the records
   need. That work is tagged and installed. cc-desk then runs the second alone, on work that is
   real and small.

The third costs one hand-over between rounds and buys a proof on cc-desk's repo before another
project depends on it.

## What goes in Go

The process will keep changing, and so will Claude Code. Go that knows either one in detail has
to be rebuilt each time. This design keeps the two kinds of knowledge apart.

Go holds what a script must do with no model. It launches and ends sessions, merges a pull
request when a recorded condition holds, counts minutes, and shows state. How a pass is planned,
reviewed, scored, and judged is text a model reads: `pass-core`, the two skills, the seven launch
templates, and the words in a release file.

Every Go change in this design passed one test, and every plan and review in the round applies
it again: if `pass-core` changed this rule next month, would the Go have to change? When the
answer is yes, the rule moves to text or to data in the release file, and Go keeps a slot that
holds it unread. The table shows what the test moved.

| The playback held | This design holds |
| --- | --- |
| A budget ratio of 2 in the code | The release file states each round's budget in minutes. Go compares two numbers |
| Standing answers with a typed stop and condition | Entries of text that a launch prompt prints. Go never reads the words |
| A verb for a plan's path and its scope | Nothing new. A plan whose scope grew stops with `pass stop --reason scope`, which is built |
| A merge refused when a file outside `docs/` changed after the review | Nothing new. The check already merges only the commit `pass ready` named (`internal/sessions/merge.go:144`). The skill's words change |
| Planning misses and a score that Go parses | One notes file that `pass ready` stores unread. `pass-body-check`, a workstation script, checks the tags |
| A count of questions answered as recommended | The report template tells the conductor to count them from the records |
| A refusal keyed on a session named `conductor-<project>` | A list of the sessions in a checkout that no record names |
| A limit of four sessions on pavilion | One message at the hand-over |
| A stale flag read from a session's job file | Nothing. A stopped pass's session is ended, which is the case the lessons hold |

The same test applies to Claude Code. cc-desk touches it in four places today: the session list
and a session's screen (`internal/sessions`), the launch and the stop (`internal/launch`), the
usage figure (`internal/usage`), and two hooks. Each read that fails says "can't tell", and the
check acts on nothing it can't read. 1.1 adds no fifth place and no new field. The list of other
sessions uses the `cwd` and `kind` the session list already gives.

Each pull request states the Go lines it added and removed outside tests, and the round's report
totals them against 11,654.

## The check takes over the watching

Today a conductor watches. It subscribes to each session and runs `round-watch`, and it acts
when one wakes it. Six of the 25 stops came from that loop. The watch missed a stopped session,
or fired while the conductor was blocked.

Keeping the watch in the conductor has one thing for it: a conductor can judge what it sees in
the same turn. Against it, a conductor is a session, and a session can be blocked, idle, or
ended. A timer can't. The timed check already runs every five minutes with no model, and it
already reads every session cc-desk started.

The recommendation, which Geoff accepted in playback, is that the check does the routine
watching and a conductor does only the judging.

The check reads three signals.

1. **A pass whose record holds a stop.** The check ends the pass's session if it is still live.
   The pass shows as stopped whatever the session says. The record is the one `pass stop`
   writes. A finished session that sits idle is already handled: past 15 minutes the check ends
   it and starts it again, twice at most (`IdleLimit` and `RelaunchLimit` in
   `internal/sessions/decide.go`).
2. **A stop with no word for Geoff.** Three stops carry a cause the check can't read: the
   relaunch limit, a launch that failed, and a block it can't classify (`relaunch_limit`,
   `launch_failed`, `unreadable_stop`). Two more cases look the same from outside. One is a
   session that finished without its pull request changing. The other is a pull request closed
   on GitHub with no answer from Geoff. Before any of the five is called Geoff's, the check
   starts the conductor once with a prompt named `cause`. That session reads the pass's last
   output, its pull request, and its checks, and it ends one of two ways. It starts the pass
   again with `pass start` and a note for the next session, or it leaves the stop for Geoff with
   a sentence saying why.
3. **A session no record names.** If its folder is a release's checkout or one of its worktrees,
   the check lists it. A background one is a session nobody started, and only the desk ends one,
   on Geoff's word. An interactive one is a terminal session of Geoff's. It is listed so that
   other sessions can see it, and the desk refuses to end it.

The conductor keeps the judgment. It reads a review, sends a fix, finds a cause, and writes the
round's report. It never waits in a loop. The check starts it for one named job, and it ends in
the turn it finishes that job. A release has one conductor record, so it runs one job at a time.
A second job waits for the check after the first one ends, oldest first.

What reaches "Needs you now" follows from the stop. A stop a session wrote for Geoff, a
permission prompt, and an expired sign-in go there at once, as they do today
(`internal/snapshot/sessions.go`). The five cases under signal 2 go there only after a `cause`
session leaves the stop for him. If that session can't start, or ends without doing either
thing, the stop goes there with what the check read, so nothing waits unseen. A stop on the
conductor's record gets no `cause` session, since that session is the conductor.
`lessons-launch` removes the one known reason for such a stop, and any other goes to "Needs you
now" with the launch's error.

The `cause` session adds one template and no rule. What it looks for, and when a pass is worth
starting again, are words in that template. Go knows only that a stop of these kinds gets one
conductor job before it reaches Geoff.

A stop the check set itself and can see has cleared is another matter, and it is the one
question in "Steps only Geoff can do".

## What a release holds now

`lessons-record` adds two lists to the release file, and `release add` reads them strictly, as
it reads every field today.

- **A budget.** Each round states its budget in worked minutes. The design writer sets the
  number from Geoff's ruling, which is "Twice the plan" (2026-11-20). A round with no budget is
  never held. A raise is a ruling at the desk that changes the number, and the file keeps each
  raise with its ruling.
- **Standing answers.** Each entry holds Geoff's words, the date, the ruling it came from, and
  whether it covers one round or the whole release. Every launch prompt for the release prints
  the entries that apply. Go stores and prints the words and never reads them. The desk records
  one when Geoff says "from now on".

A pass gains one thing. `pass ready` takes a notes file and stores it unread. The session puts
its plan's path in minutes, its planning misses, and its score there, in the shape `pass-core`
asks for. The report's conductor reads the notes of every pass in the round, and no session
reads a pull request's body for them.

### Worked minutes

A pass's worked minutes are its elapsed time, less every stop and every span in which a question
on the pass was open. Today only a stop is subtracted (`internal/state/events.go`), so time spent
waiting on a merge question counts as work and pushes every forecast late. A round's worked
minutes are the sum over its passes.

### The budget hold

When a round's worked minutes reach its budget, the check starts nothing new in that round.
Sessions already running finish. The desk holds one question, with two choices: raise the budget
or stop the round. The hold is a third limit beside the two in `Limits()`
(`internal/state/rules.go`), and the question is an ordinary question record, so the page and the
desk need nothing new to show it.

### Room for 1.2

1.2 lets Geoff set times at which he checks in, and holds what can wait until then. Three
choices here keep that open.

- A schedule would be a third list on the release beside the budgets and the standing answers,
  read by the same strict reader.
- The budget hold is a question record, so a check-in can batch it with every other question.
- Worked minutes leave out time with a question open. A question held until the next check-in
  spends none of the budget, and the forecast doesn't drift while Geoff is away.

A standing answer's words say which stop it covers. A check-in can show those answers beside the
stops they covered with no new field.

## The merge test

The desk round's pass 5 built most of this. The check merges only the commit `pass ready` named,
and the merge call itself is pinned to that commit (`cmd/cc-desk/merge.go:103`). While the pull
request's head is any other commit, the check waits (`internal/sessions/merge.go:144`). Three
things remain, and none of them tells Go how a review is done.

- The `cc-desk-work` skill says today that `--commit` is the session's last commit.
  `lessons-record` changes the words: it is the commit the whole-branch review read. A session
  that pushes after its review gets the later commits reviewed and runs `pass ready` again.
  cc-desk takes the session's word for what the review read, as it does for the verdict.
- A pull request closed without a merge gets one rule, built by `lessons-watch`
  ([pull-request-closed-without-merge.md](../follow-ups/pull-request-closed-without-merge.md),
  [close-answer-failed-stop-can-be-replaced.md](../follow-ups/close-answer-failed-stop-can-be-replaced.md)).
  The closed pull request is the stronger record. Closed by Geoff's "close" answer, the pass is
  done and marked closed, as built. Closed with that answer half carried out, the next check
  finishes the close, and a "merge" ruling that would replace the answer is refused once the
  close began. Closed on GitHub with no answer from Geoff, it is a case for the `cause` session.
- The report template tells the conductor to count the questions Geoff was asked and how many he
  answered with the recommended option, from the release's records. The design template tells
  the next design writer to propose a standing answer for each.

## Launches that clean up after themselves

- A launch that fails because cc-desk's branch or worktree is still there removes them, if they

- A release of one round writes one report, and the round's report is also the release's report

  the three gaps in
  [conductor-worktree-removal-gaps.md](../follow-ups/conductor-worktree-removal-gaps.md) close.

## The live scripts

`lessons-live` is the first round's last pass, and it proves the new check in the scratch repo
before cc-desk runs anything real.

- Each script records every session it launches and stops them all on every way out, pass or
  fail.
- Each script closes its scratch rounds and its release before it exits, so the real state
  folder holds nothing from a run.
- A finished reader's output is kept. A later phase never truncates it.
- The live run covers the three signals: a stopped pass's session is ended, a `cause` session
  runs, and a stray session is listed.
- [live-scripts-start-a-conductor.md](../follow-ups/live-scripts-start-a-conductor.md) and items
  1, 2, 5, and 6 of [desk-run-review-notes.md](../follow-ups/desk-run-review-notes.md) are
  folded in.

## The `pass-core` edits

`lessons-core` is a pass in the workstation repo. It lands the companion file's text as one pull
request, with three scripts: a new `pass-body-check`, the `claude-tooling-sync` fix, and a
`round-watch` that also exits on a blocked or done session and when nothing it reads has changed
for 20 minutes.

`pass-core` says a round's passes sit in one repo. The round plan carries a standing answer for
this exception. `lessons-core` works in a worktree of `~/.dotfiles` cut from its `origin/main`,
through the `dotfiles-pass` adapter, and the conductor lands it with `approval-queue land` as
"Close" says. The desk round's answers 22 and 23 did the same for its workstation pull requests.

`~/.claude` links into the workstation repo's main checkout, so the merge changes the rules for
every session on the machine at once. Two rounds of other projects are running. The conductor
messages `conductor-cairn-cms` and `conductor-dubplate` when the pull request merges and names
the changed headings. Their round plans' standing answers still hold, since a round plan
overrides the skill.

This round doesn't wait for that merge. Its round plan carries the same rules as standing
answers, so its first planners work under them from the start.

## When something goes wrong

- **The budget is reached.** Running sessions finish, nothing new starts in that round, and one
  question waits at the desk.
- **Weekly usage reaches 85 percent.** In the first round the conductor finishes the pass in
  flight, starts nothing, and writes its report. In the second round cc-desk's usage stop holds
  launches at the same figure. cc-desk has no settings file today, so its stop is 100
  (`DefaultUsageStop`), and the hand-over writes one that sets `usage_stop_percent` to 85.
- **Four planners or executors are working on pavilion.** In the first round the conductor waits
  for one to end. Geoff ruled that cc-desk goes first, so the other two conductors hold their
  launches while it waits. The second round runs one session, and the hand-over tells the other
  two conductors that it holds that slot until the release closes.
- **The workstation pull request can't be pulled into the main checkout.** Another session has
  uncommitted files there. The conductor writes it under "Open decisions" and goes on, since no
  cc-desk pass depends on the live text.
- **A `cause` session can't start, or ends without acting.** The stop goes to "Needs you now"
  with what the check read.
- **A read of Claude Code fails.** The check ends and starts nothing on what it can't read, and
  the page says which read failed, as it does today (`internal/snapshot/sessions.go:177`).
- **A live script dies mid-run.** Its exit trap stops its sessions and closes its release. After
  a kill no trap can catch, the next run's start stops what the last run recorded.
- **The second round's check fails in a way the first round built.** cc-desk stops launching.
  Geoff opens a terminal session in the repo, and that session files a row in the lessons file
  and fixes it as a direct change or a one-pass round.
- **A hand-over step fails.** The conductor tries the tag, the install, or `release add` once
  more after 60 seconds. If it fails again, the conductor writes the command and its output
  under "Open decisions" and ends, and the second round doesn't start. A terminal session
  resumes the hand-over from that step.
